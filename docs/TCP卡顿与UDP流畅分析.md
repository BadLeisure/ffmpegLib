# TCP 卡顿与 UDP 流畅：案例分析

> 案例环境：ffmpegLib RTSP 播放器（H.265，IP 流无 B 帧，30fps，2560×1440），RTSP over UDP/TCP 可切换。
> 日期：2026-11-07

## 一、现象

| 传输方式 | 画面平稳时 | 画面急剧变化时 |
|---|---|---|
| UDP | 流畅 | **流畅** |
| TCP | 流畅 | **有卡顿（画面冻一下再跳）** |

Wireshark 抓包确认：**TCP 模式下无丢包**——卡顿不是丢包导致的，而是**到达节奏被破坏**（"节奏丢失"）。

## 二、根因定位

### 2.1 突发的来源

画面急剧变化时，编码器瞬间产生大码率数据（一个大 I 帧可达 300KB，约 200 个 RTP 包），瞬时码率需求远超平均码率。**这个突发 UDP 和 TCP 收到的是同一份数据**，差异在于协议栈的处理方式。

### 2.2 TCP 为什么"突发变卡顿"——四个放大机制

以 300KB I 帧、链路 50Mbps、RTT 20ms 为例：

**① ACK 自时钟（分批释放）**
TCP 一次只能发送拥塞窗口（cwnd）大小的数据，然后必须停等 ACK，收到才能继续。300KB 被 cwnd=64KB 切成"64KB 脉冲 → 10ms 停顿 → 64KB 脉冲"的锯齿流；UDP 是 48ms 连续灌完。FFmpeg 组帧节奏被切成段，后续帧全部顺延。

**② 空闲后慢启动重启（本案例头号嫌疑）**
静态画面期 TCP 连接空闲 → cwnd 衰减到初始值 ~14KB。画面剧变突发到来后，TCP 从 14KB 起每 RTT 翻倍爬坡：

```
t=0 发 14KB → t=20ms 发 28KB → t=40ms 发 56KB → t=60ms 发 112KB → t≈100ms 排空
```

排空需 ~100ms（UDP 仅 48ms），期间 FFmpeg 每轮凑不齐一帧 → `av_read_frame` 阻塞 → 解码饿 → 画面冻结。**这精确解释"静止画面后急剧变化才卡"的现象**。

**③ 队头阻塞（HOL）**
TCP 字节流严格有序：任何一个 segment 延迟/重传，其后所有数据（哪怕已到达网卡）都被内核扣住不交付。WiFi 链路层 MAC 重传发生在抓包点之前的无线段上，Wireshark 在 IP 层看到的是重传成功后的包——因此"无丢包"与"传输被拉长"可同时成立，每次链路层小滞留都会把整条流卡 30ms 级。

**④ 拥塞自我减速**
突发导致 AP/路由器缓冲排队 → RTT 变大 → ACK 更慢 → 发送更慢（bufferbloat 正反馈）；一旦溢出丢包，cwnd 砍半且恢复需多个 RTT。TCP 在突发面前是"踩刹车"，UDP 没有刹车机制。

**叠加效果**：到达间隙 100~300ms → 解码饿 → 画面冻结 → 排空后突发涌入 → 迟到的帧又被播放器晚到丢帧逻辑丢弃 → 二次卡顿。

### 2.3 UDP 为什么不卡

- RTP 包各自独立、即到即用、互不阻塞，无 HOL；
- 无拥塞控制/无 ACK 等待/无慢启动，链路速率直达；
- FFmpeg 的 `reorder_queue_size=100` 内置了 UDP 乱序平滑缓冲；
- 带宽充足（Wireshark 无丢包）时，突发按物理传输时间连续到达，组帧节奏连续。

**代价**：带宽真不足时 UDP 不减速而是丢包 → 花屏直到下一个 IDR（TCP 则表现为延迟/卡顿）。

> 一句话总结：**UDP 把"带宽不够"表现为丢包，TCP 把"带宽瞬时不够"表现为延迟抖动。**

## 三、解决方案：解码前加 1~2 帧延迟预算（jitter buffer 思想）

### 3.1 原理

按 RTP 时间戳（真实媒体时序）匀速消费，允许帧最多迟到 budget 才判晚到：

- budget = 2 帧 ≈ 66ms，可覆盖 TCP 慢启动爬坡的典型到达间隙（50~150ms 区间的多数场景）；
- 间隙 ≤ budget：用缓冲帧桥接，播放节奏完全平滑；
- 间隙 > budget：超出部分才丢帧（比现状少丢很多）；
- **代价**：端到端延迟 +33~66ms（业务决策）。

### 3.2 关键认知：不缺缓冲，缺的是"允许缓冲生效的策略"

播放器已有 FrameQueue（8 帧 ≈ 266ms 缓冲，平滑档已从 12 帧缩减）和按 PTS 节奏的刷新线程——等价物已存在。现有策略是**实时优先**，会主动把缓冲清空：

| 现有机制 | 现状 | 需要调整 |
|---|---|---|
| 晚到丢帧阈值 | `kNormalLateFrames=1.8` / `kBacklogLateFrames=1.0` 帧间隔 | 引入 66ms 延迟预算：以"墙钟 − budget"虚拟时钟判定晚到 |
| 追墙钟 | 丢帧时 `frame_timer = now` | 时间轴锚定虚拟时钟，让预算稳定存在 |
| 拥塞丢帧水位 | `QUEUE_WM_MID=6 / HIGH=9`（EMA 瞬时积压即丢） | 水位上调 2~3 或加持续时间条件，TCP 突发的瞬时 backlog 不应立刻丢帧 |
| 起播节奏 | 首帧立即出 | 攒满 1~2 帧再出首帧 |

另注意：**"按 RTP timestamp 重排"在 TCP 下不需要**——TCP interleaved 字节流天然有序，无需重排，需要的是"平滑消费节奏 + 延迟预算"。

### 3.3 改动落点（方案）

- `video_refresh_thread`（ffplay.cpp）：延迟预算虚拟时钟，~20 行；
- 拥塞水位常量（ffplay.cpp `QUEUE_WM_MID/HIGH`）：上调或加条件；
- 可选：传输方式做成 `startRtsp` 可配置参数，弱网 TCP+平滑档、好网 UDP+实时档。

## 四、验证方法

1. **改前量化**：TCP 卡顿时刻抓 `video_diag`（tag `Decoder`），记录 `frame_wait_max`（饥饿深度）与 `late_drop`（追赶丢帧量）；
2. **改后对比**：同场景下 `frame_wait_max` 不变、`late_drop` 显著下降、卡顿消失/减轻；
3. **延迟评估**：对比 UDP 模式的端到端延迟，确认 +66ms 在业务可接受范围；
4. 长跑确认 budget 稳定存在（`decoded_pts_interval_ms` 稳定 ≈ 33ms）。

## 五、结论

| 维度 | 结论 |
|---|---|
| 诊断 | TCP 突发到达间隙（ACK 时钟/慢启动/HOL/拥塞减速叠加）导致解码饥饿，非丢包 ✅ |
| jitter buffer 方向 | 原理正确 ✅ |
| 落地修正 | 缓冲已存在（FrameQueue），需加 66ms 延迟预算 + 放宽晚到丢帧策略，否则缓冲被现有实时优先策略清空 ⚠️ |
| UDP/ TCP 选型 | UDP 低延迟但丢包花屏；TCP 不花屏但需延迟预算换平滑。建议做成可配置，按网络场景选择 |

## 六、后续实证与结论修正（2026-11-10~11）

### 6.1 图传行为确认（图传开发答复）

**图传 = 纯转发节点，无内部缓冲/反馈**：数据量超过图传带宽时**直接丢 IP 包**，不会积攒、不会向编码器反馈降码率。

对 TCP 链路的含义：
- 图传丢的 IP 包由**两端内核 TCP 重传**补齐 → **内容永不缺失**，只表现为延迟/停顿
- 图传丢包是三种症状的共同根源：**冻结**（重传等待）、**跳切**（反压→相机编码器丢帧）、**花屏**（编码器丢帧时参考链断裂产出的坏帧，经 TCP 原样送达）
- 反压终点在相机编码器：MediaMTX 写阻塞 → 停止读相机 → 相机编码器停产/丢帧（实测停顿期 pts 仅前进 1 帧）

### 6.2 IDR 瞬时码率数学（IDR 空档的根本原因）

IDR 是帧内编码的整帧刷新，无法压缩，**每 ~1.1s 爆发一次**：

```
IDR 124KB 若按帧节奏 33ms 内发出 → 瞬时需求 ≈ 30Mbps（远超 8Mbps 链路）
链路以满容量序列化：124KB×8 ÷ 8Mbps = 124ms   ← 链路被 IDR 独占的最短时间
```

- **健康时**：IDR 空档实测 84~148ms ≈ 124KB 在 8Mbps 上的**纯序列化时间**（分毫不差）——这是 GOP 结构的固有代价，P 帧因小（9KB→9.6ms）无此空档
- **拥塞时**：丢包重传 + 排队把序列化拉长到 **322~410ms**（实测 ✅），超出预算的部分成为可见冻结
- 顺带推论：**恢复后 30ms 灌完 1.1MB ≈ 瞬时 293Mbps** → 图传空口瞬时能力远高于 8.9Mbps 需求 → 大停顿的成因是**链路瞬断**（RF 中断/重同步），而非持续带宽不足（对之前"带宽不足"定性的修正）

### 6.3 拥塞期（需求>容量的窗口）在遥控器上的完整表现

拥塞期 = "瞬时码率需求 > 链路瞬时容量"的时间窗（需求有 IDR 尖峰，容量随无线信号波动，两者叠加成阵发拥塞）。以实测 322ms 空档 episode 为例：

| 墙钟 | 事件 | 观感 |
|---|---|---|
| 15:50:09.562 | 322ms 到达中断（IDR 132KB）| 冻结开始 |
| 15:50:10.038 | 内容跳 2.3 帧（反压→相机丢帧）| 跳切 |
| 15:50:10.422 | IDR 前空档 114ms | 小顿 |
| 15:50:11.394 | IDR 到达（前空档 89ms）| 小顿 |
| 15:50:11.985 | 107ms 间隔 | 微顿 |
| 15:50:12.802 | 410ms 到达中断（IDR 147KB）| 第二次冻结 |

覆盖原理：FrameQueue 存货帧按 33ms 节奏顶住空档前段（存货 N 帧 = N×33ms），66ms 预算容忍恢复帧的迟到；**存货+预算（~126ms）能覆盖健康空档（84~148ms）的大部分，覆盖不了拥塞膨胀空档（322~410ms）**——超出部分就是可见卡顿。

### 6.4 双流实证（138.1s 录制，main 1600×992 + sub 2560×1440 同时拉流）

| 指标 | 旧录制（8.94Mbps 超载图传）| 本次（4.07+0.54=4.6Mbps，峰值 7.05Mbps）|
|---|---|---|
| 平均帧率 | 25.7fps | **29.5fps**（接近标称 30）|
| 缺帧比例 | 8.7% | **1.4%** |
| 最大到达中断 | 1572ms | **456ms** |
| 最大内容跳跃 | 1137ms | **137ms** |
| 坏帧 | 100 帧/10 区间 | 27+5 帧/2 区间 |

**码率降到容量以内后，冻结/跳切/坏帧全部大幅收敛**——反向验证了拥塞根因。双流同瞬间停顿（main 706ms 与 sub 727ms 仅差 7µs）实锤共享图传瓶颈。

### 6.5 剩余长尾（相机端待整改）

- 编码器仍丢 ~1.4% 帧（单帧跳为主）→ 30fps 不达标，轻微抖动
- 偶发（2 次）单帧跳破坏参考链 → 15 帧坏帧 → 短暂花屏
- **相机端整改项**：① 编码器过载丢帧后强制插 IDR；② 排查 30fps 不达标原因
- 验证命令：`ffmpeg -v error -i main.h265 -f null -`（POC 错误 = 坏帧实锤）
