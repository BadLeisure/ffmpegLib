# 从流媒体服务器拉流到遥控器显示：全链路分析（TCP / UDP）

> 适用工程：ffmpegLib（Android NDK + FFmpeg + JNI 的 RTSP 播放器）
> 链路：相机 --有线--> MediaMTX --图传(无线)--> 遥控器(地面站)
> 编写日期：2026-11-09。行号引用以当前代码为准。

---

## 一、端到端链路总览

```
【无人机侧】                                    【图传无线链路】              【遥控器(地面站)】
相机 --有线--> MediaMTX 应用缓冲
                ↓ write()
          主机内核发送缓冲 (Send-Q)  ◄─ 挤压点⓪
                ↓ TCP 按 min(cwnd,rwnd) 分段发出 / UDP 直接发
          图传发射机 TX 队列        ◄─ 挤压点①：等空口，满了丢包(UDP)或排队(TCP)
                ↓ 无线空口（丢包/乱序/静默发生在这里）
                                        地面站网卡 → 内核接收缓冲 (Recv-Q) ◄─ 挤压点②
                ↓ FFmpeg 重组出完整帧（av_read_frame 返回）
          读线程 → PacketQueue → 解码线程 → FrameQueue → 刷新线程
                ↓ handleFrame → 双缓冲 → onI420Data
          Java 层 GL 上屏
```

四级缓冲（①②③④④'）+ 一条反压链（TCP 模式下：地面站读得慢 → MediaMTX 写阻塞 → 停止读相机 → 相机编码器停产/丢帧）。

### 1.1 三段链路的容量与丢包特性（有线 / 无线）

图传链路其实是三段，容量和丢包特性完全不同——**"图传带宽"特指中间的无线空口段**：

| 段 | 介质 | 容量 | 会丢包吗 |
|---|---|---|---|
| MediaMTX → 图传发射模块 | **有线**（无人机内部网口/USB）| 100Mbps 级 | ❌ 几乎不丢（有线误码率可忽略）|
| **图传发射模块 → 无线空口 → 接收模块** | **无线** | **图传带宽（如 8Mbps）** | ✅ **唯一的丢包/拥塞段** |
| 接收模块 → 遥控器 | **有线**/USB | 100Mbps 级 | ❌ 不丢 |

要点：

1. **"图传带宽 8Mbps"的准确含义**：无线空口每秒最多能把 8Mbps 的数据从无人机侧送到遥控器侧——拉流的每个字节都必须跨越这一段，它是整条端到端链路的瓶颈；
2. **丢包只发生在空口段**：MediaMTX 灌入 TX 模块的速率（如 8.5Mbps）超过空口容量 → TX 队列积攒 → 满 → 丢 IP 包（图传开发已确认：纯转发，超带宽即丢，不缓冲不反馈）；
3. **有线段永不丢包** → 因此 TCP 的重传全部由 MediaMTX 端到端负责（图传不重传应用数据；图传自身的链路层 FEC/ARQ 对 TCP 透明，纠不回来的才上升为 IP 丢包）；
4. **双向共用注意**：FPV 图传通常下行传视频 + 上行传遥控指令。若 8Mbps 是空口**总容量**且上下行按 TDD 时隙共享，则**实际给下行视频的可用带宽 < 8Mbps**（如对半分则仅 ~4Mbps）——码率红线必须按"下行实际可用份额"设定，务必向图传开发确认容量口径（是物理总容量还是下行份额）。

观测：三段的容量与丢包可用 iperf3 实测——跨图传打流即实测空口段；`iperf3 -u -b 30M` 直接报告纠错后的残余丢包率。

## 二、FFmpeg 框架内部：av_read_frame 之前发生了什么

`av_read_frame()` 是"帧世界"和"包世界"的分界线：**线以下是 RTP 包（≤1500B、乱序、会丢），线以上是帧级 AVPacket（完整、有序、带 pts）**。

### 2.1 连接建立与传输选择（RtspPlayer.cpp:660~676）

```cpp
av_dict_set(&opts, "rtsp_transport", "tcp", 0);   // 当前配置
av_dict_set(&opts, "stimeout", "3000000", 0);
av_dict_set(&opts, "probesize", "512000", 0);
av_dict_set(&opts, "analyzeduration", "200000", 0);
av_dict_set(&opts, "reorder_queue_size", "100", 0); // 仅 UDP 生效
av_dict_set(&opts, "buffer_size", "524288", 0);
```

- **RTSP 控制通道（DESCRIBE/SETUP/PLAY + SDP）永远走 TCP**；`rtsp_transport` 只决定 RTP 媒体数据的承载方式。
- SDP 里的 `sprop-vps/sps/pps` 被 FFmpeg 填进 `codecpar->extradata`（Annex B 格式），供解码器初始化和录制文件头使用。

### 2.2 TCP 路径（rtsp_transport=tcp，RTP interleaved）

```
libavformat/rtsp.c : rtsp_read_packet()
    从 RTSP 字节流解析 interleaved 头（'$' + channel + length），
    按 channel 分离 RTP / RTCP
  ↓
libavformat/rtpdec.c : rtp_parse_packet()
    解析 RTP 头（sequence / timestamp / marker / SSRC）
  ↓
libavformat/rtpdec_h265.c : h265_handle_packet()
    按 RFC 7798 处理三种形态：
    · 单 NALU 包 → 直通
    · FU 分片包 → 按序拼装成完整 NALU（一个大帧拆几十上百个 FU）
    · AP 聚合包 → 拆成多个小 NALU
    同一 RTP timestamp 的 NALU 归组为同一个访问单元（一帧）
  ↓ 一帧的全部 NALU 到齐（收到下一帧的首包或 marker 位）
    加 Annex B 起始码 → 填 pts(=RTP timestamp 换算 90kHz)/dts
  ↓
libavformat/utils.c : av_read_frame() 返回 AVPacket（帧级）
```

TCP 特性：字节流**有序且不丢**（内核重传兜底）——重组器的输入永远完整。代价是**队头阻塞**（丢 1 段，后面全等）和 **cwnd 整形**（突发被切批）。

### 2.3 UDP 路径（rtsp_transport=udp，RTP over UDP）

```
UDP socket 收包（每个 RTP 包独立数据报）
  ↓
rtpdec 重排队列（reorder_queue_size=100 包，ffmpeg 内部 jitter buffer）
    按 seq 排序；等前置包或超时
  ↓ 缺失的 seq = 永远等不到 → 该访问单元残缺或被丢弃
  ↓ 其余同 TCP 路径的 h265_handle_packet 重组
av_read_frame 返回【完整或残缺】的 AVPacket
```

UDP 特性：无重传、无 HOL，**到达节奏按线速直达**（流畅），但丢的 IP 包 = 丢的 FU 分片 → **残缺帧直接进解码器 → 花屏**。

### 2.4 中断机制（读线程的"超时保险丝"）

RtspPlayer.cpp:833~834：

```cpp
armInterruptTimeout(kReadInterruptTimeoutUs);   // 2 秒
const int ret = av_read_frame(fmtCtx, pkt);
clearInterruptTimeout();
```

`AVFormatContext->interrupt_callback`（RtspPlayer.cpp:180 `ffmpegInterruptCallback`）在 FFmpeg 内部的阻塞循环里被周期性回调：超过 2s 没拿到完整帧 → 回调返回 1 → `av_read_frame` 以 `AVERROR_EXIT` 退出 → 读线程转 WaitRetry 重连。**注意：中断点在帧边界，不会造成 TCP 流 desync**（实测最大停顿 1.57s < 2s，未触发）。

### 2.5 TCP/UDP 发送层差异：字节流 vs 数据报

体系里共有四种"包"，分属四层，"丢包/重传"的粒度各不相同——**TCP 重传的"包"和 `av_read_frame` 拿到的"包"不是同一个东西**：

| 层 | "包"是什么 | 典型大小 | 丢失后果 |
|---|---|---|---|
| ④ AVPacket | av_read_frame 返回的完整帧（RTP 重组后）| 几十~几百 KB | 不上网络，谁都不会丢 |
| ③ RTP 包 | 帧的分片（带 RTP 头）| ≤~1500B | **UDP 模式**丢失 → 帧缺片 → 花屏 |
| ② TCP segment | 字节流的片段 | ~1460B（MSS）| **TCP 模式**丢失 → 内核重传 → 只是延迟 |
| ① IP 包 / 图传空口帧 | 链路层封装 | 链路决定 | 触发上层对应机制 |

**TCP 发送 = 往"字节管子"里写，怎么切由内核决定：**

```
应用：write(RTP包1) + write(RTP包2) + write(RTP包3) → 全部追加到同一条字节流
内核：按 MSS(≈1460B) 切 segment，切分位置与 RTP/帧边界毫无关系
接收：按字节序号重组出【一模一样的字节流】→ FFmpeg 再解析 '$' 框架还原 RTP 包
```

- 消息边界丢失：接收方看到的是流，丢一个 segment = 缺一段字节 → 重传该段 → **字节流复原后帧必然完整**（丢包只表现为延迟）；
- 发送节奏被 cwnd/ACK 整形：写进 Send-Q ≠ 发上网络，内核按窗口分批放行——这就是每个 GOP 边界 IDR 到达空档 100~300ms 的机制来源。

**UDP 发送 = 一次 sendto 一个完整独立包裹，边界保留：**

```
应用：sendto(RTP包1)、sendto(RTP包2)... 每个报文独立封装成 IP 包
内核：不切、不重传、不排序、不限速——应用推多快就发多快，队列满直接丢
接收：报文整体到达或整体丢失（没有部分到达）；乱序由 reorder 队列重排
```

- 丢失粒度 = 整个数据报：丢一个 = 丢一个 RTP 包 = 帧缺一片 → 解码花屏；
- MTU 注意：超过 MTU 的数据报会被 IP 层分片，**任何一个分片丢失 = 整个数据报报废**（丢包率被放大数倍），因此 RTP over UDP 的分片在 RTP 层完成（FU 机制），保证每个数据报 ≤ MTU；
- 无整形：IDR 突发按线速直达（UDP 模式下 IDR 到达无空档、不卡顿的原因）。

**两种"丢包"的最终形态对照：**

| | TCP | UDP |
|---|---|---|
| 空口丢包后 | 内核重传该 segment → 字节流复原 → **帧永远完整** | 数据报永久丢失 → **残缺帧** |
| 应用层感知 | 只有延迟（丢包对应用无感）| 直接花屏 |
| 协议层不管的 | 延迟大小 | 可靠性/顺序/发送节奏（全要端上自己做）|

### 2.6 TCP 传输细节：内核链路、缓冲拷贝、拥塞控制与重传

#### A. 一次 write/read 的内核路径（字节在各缓冲间的流动）

**发送方向（MediaMTX 侧）：**

```
MediaMTX 调 write(buf)
  ① 拷贝进该 socket 的内核发送缓冲 Send-Q（copy_from_user）
     → write() 返回（≠对端收到，只表示"字节已交给内核"）
  ② 内核 TCP 按 min(cwnd, rwnd) 允许的量，把 Send-Q 字节切成 segment
  ③ IP 封装 → 网卡 → 图传空口
  ※ 已发出但未被 ACK 的 segment 在 Send-Q 里保留副本（用于重传）
  ※ ACK 覆盖后副本才释放 → Send-Q 有空位 → write 才能继续写
```

**接收方向（遥控器侧）：**

```
网卡收到 IP 包 → 内核协议栈校验
  ④ 按序数据 → 直接追加进 socket 接收缓冲 Recv-Q
     乱序数据（缺口之后）→ 挂在内核乱序队列暂存，不交付
  ⑤ 缺口补上后 → 乱序队列按序接上，一次性转入 Recv-Q
  ⑥ FFmpeg 的 av_read_frame → 内核从 Recv-Q 按序拷贝到应用缓冲（copy_to_user）
     → 解析 RTSP interleaved 框架 → 还原 RTP → 重组帧 → 返回 AVPacket
```

三条铁律：
- **write() 返回 ≠ 对端收到**：只表示字节进了 Send-Q，真正的送达由内核异步完成；
- **数据进入 Recv-Q 后就不会再丢**（对应用而言）——FFmpeg 读得慢只是让 Recv-Q 堆积（占用的额度会让对端发送窗口收紧）；
- **端到端字节序等式**：MediaMTX 写入的字节序 = FFmpeg 读出的字节序——中间的乱序/丢包/重传/整形全部由两端内核吸收，应用完全无感。

#### B. 拥塞控制四件套（cwnd 的生命周期）

发送速率闸门 = **min(cwnd, rwnd)**：cwnd 防"压垮网络"，rwnd 防"压垮接收方"。

| 阶段 | 触发 | 行为 |
|---|---|---|
| **慢启动** | 新连接 / cwnd 塌陷后重启 | cwnd 从初始值（10 MSS ≈ 14KB）每 RTT **翻倍**指数爬坡 |
| **拥塞避免** | cwnd 超过 ssthresh 后 | 每 RTT **+1 MSS** 线性增长（温和探测）|
| **快速重传 + 快速恢复** | 收到 3 个重复 ACK（+SACK）| 立即重传缺失段，cwnd **减半**（不塌底），线性增长继续 |
| **RTO 超时** | 定时器超时（重传也失败）| cwnd **塌回初始值**，RTO 指数退避（200ms→400→800ms…），重新慢启动 |

**空闲衰减**：连接空闲超过约 1 个 RTO → cwnd 收缩回初始值（网络状况可能已变，旧探测结果作废）→ 下次突发重新慢启动。
**你的场景对应**：静态画面（连接空闲）→ cwnd 冷却 → 剧变时 300KB 突发从 14KB 爬坡 → 每个 GOP 边界 100~300ms 到达空档（实测 44 次对齐 IDR ✅）。

#### C. 重传机制两条路径

| | 快速重传 | RTO 超时重传 |
|---|---|---|
| 触发 | 3 个重复 ACK（+SACK 清单）| 定时器超时 |
| 前提 | 缺口后还有数据不断到达 | 缺口后静默（无后续数据或全丢）|
| 重传内容 | 只重传缺失段（SACK 精确补洞）| 缺口段及其后全部（无 SACK 时）|
| 发现耗时 | ~1 个 RTT（几十 ms）| 200ms~1s 起，指数退避 |
| cwnd | 减半 | 塌回初始值 |
| 对应现象 | GOP 边界微顿 | 693~1572ms 大冻结（实测递增 ✅）|

重传次数累计超过内核上限（tcp_retries2 ≈ 15 次退避）→ **TCP 主动 RESET 断连** → MediaMTX write 报错 → 会话终结（等待重连）。

#### D. 内核机制 ↔ 实测现象对照

| 内核机制 | 你观察到的现象 |
|---|---|
| 慢启动爬坡（空闲衰减后）| 每个 GOP 边界的 IDR 到达空档 100~300ms |
| Send-Q 堆满 → write 阻塞 | MediaMTX"管道变细"、反压传导至相机编码器 |
| 乱序队列暂存 | 停顿期 FFmpeg 收不到数据（recv_us 静默）|
| 缺口补上 → 乱序队列按序交付 | 恢复瞬间突发灌包（28 帧/30ms）|
| RTO 指数退避 | 5 次大冻结时长递增（693→1572ms）|
| RetransSegs 计数 | 内核重传活动的量化（`ss -ti`/`/proc/net/snmp` 可观测）|

## 三、TCP 模式全链路（逐阶段）

以 20 个包（4 帧：A=IDR 8 包、B/C/D 各 4 包）从 MediaMTX 到屏幕为例：

| 阶段 | 位置 | 行为 | 阻塞/异常点 |
|---|---|---|---|
| ① 应用层 | MediaMTX | `write()` 把 20 包拷进 Send-Q 即返回 | Send-Q 满 → write 阻塞 → 反压开始 |
| ② 发送内核 | MediaMTX 主机 | 按 cwnd 分批发出（初始 10 包）| 丢包 → cwnd 减半/塌陷 → 速率爬坡 |
| ③ 图传链路 | 无线空口 | 按链路速率排空队列 | 拥塞丢 IP 包 → 触发 TCP 重传 |
| ④ 接收内核 | 遥控器 | 按序交付 Recv-Q；乱序的扣住等缺口 | 缺口补上才一起交付（队头阻塞）|
| ⑤ FFmpeg 重组 | av_read_frame 内 | RTP 重组出完整帧 | 等 2s 触发中断重连 |
| ⑥ 读线程 | RtspPlayer.cpp:834 | 返回帧 → 录制(880) → 关键帧门控(891) → SEI(934) → 入队(935) | — |
| ⑦ 解码线程 | ffplay.cpp:207/518 | packet_queue_get → 送硬解 → 帧池取壳 → FrameQueue | 队列空 → 阻塞 |
| ⑧ 刷新线程 | ffplay.cpp:320/638 | frame_queue_pop → 预算判定 → handleFrame | 队列空 → 阻塞 = 画面冻结 |
| ⑨ 显示 | RtspPlayer.cpp:576 | 双缓冲写 → swap → JNI onI420Data → GL | — |

### TCP 拥塞/丢包的三个机制（发生在 ②③④）

| 机制 | 触发 | 表现 |
|---|---|---|
| **快速重传** | 接收方 3 个重复 ACK | 一个 RTT 补上缺口，应用仅顿 20~50ms |
| **RTO 超时重传** | 重传也丢 / 连续多包丢 | 静默 200ms~1s，指数退避（实测 693→1572ms 递增 ✅）|
| **cwnd 塌陷+慢启动** | 拥塞/连接空闲后 | IDR 突发被切批，每个 GOP 边界到达延迟 100~300ms（实测 44 次对齐 IDR ✅）|

### TCP 反压链（带宽不足时的传导）

```
图传带宽 < 瞬时码率（实测稳态 8.9Mbps，500ms 峰值 26.6Mbps）
→ ④接收变慢/③链路排队 → ⓪MediaMTX write 阻塞
→ MediaMTX 停止读相机（RTSP reader 慢不会静默丢包，只会反压或断连）
→ 相机推送阻塞 → 编码器输出队列堆积
→ 编码器【主动丢帧】(pts 跳跃=内容缺失) 或【停顿】(冻结)
→ 恢复时补 IDR + 突发灌包
```

判定方法：MediaMTX 主机 `ss -tin dst <地面站IP>` 看 Send-Q 顶满 + retrans 上涨；有线段抓包看相机流是否同步暂停。

## 四、UDP 模式全链路（与 TCP 的差异点）

| 阶段 | TCP | UDP |
|---|---|---|
| MediaMTX 发送 | 写 TCP socket，阻塞→反压 | 写 UDP socket，**从不阻塞**；内核/链路满了静默丢 |
| 图传链路丢包 | TCP 重传补齐 → 内容不缺，只延迟 | **真丢 → FU 分片缺失 → 残缺帧 → 花屏** |
| 到达节奏 | cwnd/ACK 整形 → 脉冲 + GOP 边界空档 | 线速直达 → 节奏连续（流畅的原因）|
| FFmpeg 重组 | 输入完整，帧要么完整要么是编码器产出即坏 | 缺分片 → 吐残缺帧或丢 AU |
| 端上配合 | 延迟预算吸收抖动 | reorder 队列吸收乱序（+延迟）|
| 弱网表现 | 冻结 + 跳切（坏帧来自相机） | 花屏（自己丢的）+ 冻结 |
| 延迟 | 高（重传+整形+反压） | 低（无重传）|

一句话：**UDP 把"带宽不够"表现为丢包（花屏），TCP 把它表现为延迟（卡顿）+ 反压（相机丢帧→跳切）**。

## 五、播放器内部管线与三个队列（ffplay 层）

### 线程与队列

```
读线程(RtspPlayer)   ──packet_queue_put──►  PacketQueue(链表,4MB/500包水位)
                                                   │ packet_queue_get(阻塞点②)
解码线程 video_thread(ffplay.cpp:207) ──frame_queue_push──► FrameQueue(8帧环形,池10)
                                                   │ frame_queue_pop(阻塞点③)
刷新线程 video_refresh_thread(ffplay.cpp:320) ──handleFrame(RtspPlayer.cpp:576)
                                                   │ 双缓冲 + JNI
Java 层 onI420Data → GL 上屏
```

- **阻塞点②**：`decoder_decode_frame` 内 `packet_queue_get(queue_, &pkt, 1)`（ffplay.cpp:518）——队列空则挂起。
- **阻塞点③**：`frame_queue_pop` 的 `frameCond.wait`（ffplay_def.cpp:638）——队列空则挂起，**挂起多久 = 画面冻结多久**。

### 刷新线程的显示时钟（ffplay.cpp:320~470）

```
pop 出帧 → 检查 generation(切流重置) → 计算 pts_s
delay = pts差；异常(≤0或>1s)用 EMA 平滑值替代
target_time = frame_timer + delay
晚到判定(now - target > late_threshold + kDisplayBudgetSec) → 丢帧,frame_timer=now 重锚
未晚到 → sleep(min(剩余,sleep_cap)) → handleFrame → frame_timer = callback_end
首帧(含切流后)：av_usleep(66ms) 攒帧再出（ffplay.cpp:390）
```

- 旧追实时档：判定阈值 ≈ 1.8×帧间隔(60ms)，显示时钟贴墙钟 → 迟到即丢，延迟 0~33ms，抖动变顿挫；
- 新平滑档：阈值 + 66ms 预算 = **晚到 126ms 内都显示**，稳态延迟 66~132ms，100~130ms 到达间隙被缓冲吸收。

### 播放器自身的丢帧点（为什么它们不会造成花屏）

| 丢帧点 | 丢什么 | 为什么不花屏 |
|---|---|---|
| PacketQueue 水位丢包（ffplay_def.cpp:215）| 丢**未送解码**的新到非关键帧；关键帧到达则清队重启 | 洞永远在解码位置之后，解码器看不到洞；关键帧清队=从 IDR 干净重启 |
| PacketQueue flush（切流/重连）| 整队清空 + avcodec_flush_buffers | 解码状态全重置 |
| FrameQueue 自适应丢帧（ffplay_def.cpp:545）| 丢**已解码**的帧（最老 P/新 P）| 显示跳帧，不影响解码正确性 |
| 晚到丢帧（ffplay.cpp:424）| 丢**已解码**的迟到帧 | 同上 |

**结论：花屏的唯一来源是"输入码流里引用断裂的帧"**——即编码器产出的坏帧（TCP）或 UDP 丢分片导致的残缺帧。播放器自身的三类丢帧只造成"跳帧/冻结"，不产生花屏。

## 六、弱网异常机理大全（现象 ↔ 机理 ↔ 实证）

| 现象 | TCP 机理 | UDP 机理 | 实证（main.h265 案例）|
|---|---|---|---|
| **微顿**（100~300ms 规律性）| IDR 突发被 cwnd/ACK 整形 → 每个 GOP 边界到达空档 | 少见（IDR 直达）| 55 次到达中断，44 次对齐 IDR ✅ |
| **冻结**（0.7~1.6s）| 链路瞬断 + RTO 退避静默 + HOL；反压致相机停产 | 链路中断；相机不受反压影响 | 5 次：693/813/957/1126/1572ms，pts 仅前进 1 帧 ✅ |
| **跳切**（内容突然前跳）| 反压 → 编码器批量丢帧（引用链一致→不花屏）| 丢整帧包 | 84 处 pts 跳跃，合计 ~5.7s ✅ |
| **花屏** | 编码器过载产出引用断裂帧（TCP 忠实送达）| RTP 分片丢失 → 残缺帧 | ffmpeg 解码 100 帧 `Could not find ref with POC`，10 个区间 ✅ |
| **黑屏** | 长断流 + 无 IDR + 门控不开 | 同 | 无证据（IDR 周期 1.11s，首包即 IDR）|
| **延迟累积** | 队列积压（预算容忍）+ RTO 退避 | reorder 等待 | schedule_late 峰值 438ms ✅ |

各现象的恢复点：冻结/跳切自然恢复；花屏等下一个 IDR；黑屏走 5s 无包强制重连。
